## 0. How to use this document

1. **Never skip §2 (Ground Truth).** It records what actually exists today,
   verified by reading the code on 2026-08-12 — not what the older docs claim.
   Several repo docs are stale (see §2.6).
2. **Work phases in order.** §4 phases are sequenced by dependency, not by
   excitement. Phase A unblocks nothing else but is the highest user-visible
   defect; Phase C depends on B; E depends on D.
3. **Every phase has an Acceptance Gate.** A phase is not "done" until every
   box in its gate is ticked with real evidence (a command's output, a browser
   check). "It looks right" is not evidence.
4. **Open questions in §6 block their phase.** Do not guess a design decision
   that is listed there — ask.
5. **Update §7 (Progress Log) as phases complete.** That is how the next
   session knows where it is.

## 4. Phases

### Phase A — Hero renders on mobile

**Defect:** the hero animation is not visible on any mobile device; the poster
stays.

**Hypotheses, in order of likelihood.** These are *candidates to verify*, not
confirmed causes — Phase A begins with diagnosis, not with edits.

1. **`failIfMajorPerformanceCaveat: true`** in `probeWebGL2()` (`gate.ts:40`).
   This flag makes browsers return `null` on many mobile GPUs and in software-
   rendering situations even when WebGL2 is perfectly usable. Strongest
   suspect — it single-handedly forces Tier 0 (poster, permanently).
2. **`deviceMemory < 4` → Tier 0** (`gate.ts:22`). Chrome on Android commonly
   reports `2` or `4` on mid-range devices. A `4` passes; a `2` does not. This
   would knock out a large share of real phones.
3. **`h-svh` sticky scroll region.** The hero uses `sticky top-0 h-svh` inside a
   `REGION_VH = 400` region. Mobile URL-bar collapse changes the viewport unit
   mid-scroll, which can break sticky positioning and make the scroll-driven
   beats never advance.
4. **Tier 1 asset path.** Tier 1 loads a 2500-node mobile dataset. Confirm the
   mobile branch actually fetches and mounts rather than silently failing.

**Work:**
- Add a temporary diagnostic (dev-only) that surfaces the tier decision and the
  reason on-device — do not guess from a desktop emulator alone.
- Verify on a **real** device (or BrowserStack), not just Chrome DevTools device
  mode: DevTools does not reproduce `deviceMemory` or GPU-caveat behaviour.
- Fix the identified cause(s). Expected shape: drop
  `failIfMajorPerformanceCaveat`, lower/remove the `deviceMemory` threshold, and
  replace `svh` with `dvh` (or a JS-measured height) if #3 is confirmed.
- Keep the poster fallback ladder intact — it must still work for genuine
  Tier 0 devices and for reduced-motion.

**Acceptance Gate A:**
- [ ] Root cause identified and written into this doc's §7, with the evidence.
- [ ] Hero animates on at least **two** real phones (one Android, one iOS).
- [ ] Reduced-motion still shows the poster only, on mobile and desktop.
- [ ] A device that genuinely fails WebGL2 still gets the poster (no black box).
- [ ] `npm run check:bundle --workspace=web` still passes.

### Phase B — Neural network guides through projects

**Defect (owner-reported):** the guide moves too fast on scroll, and the
highlighted neurons show "different stuff" rather than projects.

**Confirmed cause of the wrong content:** `labelNodes` is built from *both*
`projectNodes` and `skillNodes` (`NeuralFace3DScene.tsx` ~554–570), and the
scene labels the 3 nearest. Skills therefore compete with — and often beat —
projects for the label slots.

**Target behaviour (owner spec):**
- The camera rail passes **through the project neurons in a deliberate order**.
- Each project neuron is the labelled focus while the camera is near it.
- Neurons *not* on the guided path are **skills** used in those projects —
  agentic AI, LLMs, prompt engineering, and similar.
- **Low-level / foundational skills appear at the start and the end** of the
  neural-network scroll.

**Work:**
1. **Rail redesign** — replace the nearest-neighbour walk with an ordered path
   over `projectNodes`. Ordering should be **chronological** so the dive tells
   the same story as the Timeline (§E). Requires project dates in the graph
   data.
2. **Label policy** — label **projects only** while on the guided path.
   Skills may still render as nodes (and may label on close proximity), but must
   never displace the current project.
3. **Dwell + pacing** — the "too fast" complaint is a pacing problem. Two levers:
   (a) add a dwell/ease-out at each project waypoint so the camera settles
   rather than sweeping past; (b) raise `REGION_VH` above 400 to buy scroll
   distance. Prefer (a) first — lengthening the region makes the page feel long
   without fixing the sensation of being rushed.
4. **Skill placement** — regenerate the graph so foundational skills sit at the
   spatial start and end of the rail. This is a change to
   `scripts/enrich-hero-network.ts` and a `npm run hero:enrich` regeneration.
5. **Skill taxonomy** — skills currently come from project `tags`, which are
   tech tags, not the agentic-AI vocabulary the owner wants. Either populate
   `skillsLearned` on projects (preferred — it also fixes D-052.7 FIX 4's
   honest limitation) or introduce a curated skill list. **See Open Question 3.**

**Acceptance Gate B:**
- [ ] Scrolling the dive visits every published project in chronological order.
- [ ] The labelled node while on the path is always a project, never a skill.
- [ ] Foundational skills are visible at both ends of the dive.
- [ ] Camera motion has no frame-to-frame jump above the D-052.7 measured
      ceiling (max step ≤ 0.055).
- [ ] Fast scrolling does not skip past projects without them registering.
- [ ] Regenerated `hero-face-3d.json` still within its gz budget (≤160 kB).
- [ ] `check:bundle` passes.

## 5. The bundle budget risk

**This is the most likely way V2 fails technically.**

`/` was ~151 kB against a hard 170 kB CI ceiling with four beats. V2 adds
Posts (×2 blocks), Timeline, and Gallery. Roughly **19 kB of headroom** for
three feature areas.

**Mitigations, in preference order:**
1. **Server components by default.** Posts, Timeline and the Gallery strip can
   all render server-side. The gallery cluster already proves a rich,
   scroll-animated section can cost **0 kB** of client JS by using CSS
   `animation-timeline: view()`.
2. **CSS-driven motion, never a JS animation library.** GSAP is banned from `/`
   by CI anyway.
3. **Server-side markdown.** Never ship a markdown parser to the browser.
4. **Measure after every phase**, not at the end. `check:bundle` after C, D, E
   and F individually — discovering a 25 kB overshoot at the end means not
   knowing which of three features caused it.

**If the ceiling is genuinely reached:** raising it is a `DECISIONS.md`-level
change, not a quiet edit to the guard. Justify it with measured LCP/TBT impact.

## 8. Working discipline (non-negotiable)

1. **One phase at a time.** Do not start E while B is unverified.
2. **Verify before claiming.** Every "done" needs command output or a browser
   observation. If something could not be verified, say so explicitly and why.
3. **Never run a production build while a dev server is running** — it corrupts
   `.next` and produces confusing stale-state failures. This has already
   happened twice in this project.
4. **Diagnose before editing.** Phase A in particular starts with measurement;
   the two mobile hypotheses are plausible but unconfirmed.
5. **Commit per phase**, with the acceptance gate results in the commit body.
6. **Owner review gates**: hero motion, timeline design, and all public copy
   are the owner's call, not the implementer's.
